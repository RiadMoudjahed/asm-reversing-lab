# Quiz: 22. Managed code: .NET

Answer first, then open the answer.

**1. Why does a decompiler usually recover more from a managed assembly than from a native executable?**

<details>
<summary>Answer</summary>

The assembly keeps the names of types, methods and fields, their typed signatures and the structure of the code in its metadata and IL, because the runtime needs them. A native executable has machine instructions with the names and types removed, and the decompiler has to infer them.

</details>

**2. Name three signs in triage that a file is a managed assembly.**

<details>
<summary>Answer</summary>

`file` reports `Mono/.Net assembly`; the import table has a single entry from `mscoree.dll` (`_CorExeMain` for a program); data directory number 14 (the CLR header) is not empty; and the metadata begins with the signature `BSJB` and a version string such as `v4.0.30319`.

</details>

**3. Why does `strings` with its default settings not show the string literals of a managed program?**

<details>
<summary>Answer</summary>

The literals are stored in the `#US` heap as UTF-16 text. The default search looks for single-byte characters. Use `strings -el` to find UTF-16 text, or read the heap with a script. Names of types, methods and fields are in `#Strings` in UTF-8 and do appear.

</details>

**4. What does the IL sequence `ldarg.0`, `ldfld`, `ldc.i4 499`, `add`, `stloc.0` do?**

<details>
<summary>Answer</summary>

It pushes `this`, replaces it with the value of a field, pushes the constant 499, replaces both with their sum, and pops the result into local variable 0. It is the evaluation-stack way of writing `x = field + 499`.

</details>

**5. A decompiled method uses variables called `num`, `num2` and `num3`. Where did the original names go, and how can you get them back?**

<details>
<summary>Answer</summary>

Names of local variables are stored in the debug file (the PDB), not in the assembly, so a build without one has only numbered slots and the decompiler invents names. If you have the PDB, decompile with the option that uses it (`-usepdb`). Otherwise name the variables yourself from how they are used.

</details>

**6. A class in the decompiled output is named `<>c__DisplayClass1_0`. What is it?**

<details>
<summary>Answer</summary>

A helper class generated by the compiler, not written by the author. This one holds a local variable that a lambda captures, and the lambda's body is a method of the class. Names that contain `<` and `>` mark generated code and are read as the code they implement.

</details>

**7. When should you read the IL instead of trusting the decompiled C#?**

<details>
<summary>Answer</summary>

When the decompiled code looks wrong or odd, when a detail decides the answer (a constant, a comparison, the order of operations), and when the code is obfuscated enough that the decompiler gives up. The decompiler makes choices; the IL is what the runtime executes.

</details>

**8. How do you deal with strings that an obfuscator encrypted in a managed assembly?**

<details>
<summary>Answer</summary>

The `#US` heap has few literals and the code calls one small method that returns a string. That method is the decoder: read its IL and reimplement it, or call it from a test harness in the isolated lab with the arguments you read from the call sites, as in module 20.

</details>
